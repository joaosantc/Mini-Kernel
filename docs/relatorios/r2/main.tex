\begin{abstract}
This report documents the continuation of the minimal 32-bit RISC-V operating system kernel for the Operating Systems course. The completed tasks include page-aligned physical memory allocation (Task 6), cooperative process management with context switching (Task 7), Sv32 two-level paging and virtual memory activation (Task 8), userland application build, runtime, and binary embedding (Task 9), and user mode (U-Mode) privilege transition with exception handling (Task 10). All implementations were verified on the QEMU emulator.
\end{abstract}

\begin{resumo}
Este relatório apresenta a continuidade do desenvolvimento de um kernel mínimo para a arquitetura RISC-V de 32 bits na disciplina de Sistemas Operacionais. Foram implementadas as cinco etapas da segunda entrega: alocação de memória física por páginas de 4~KB (Trabalho 06), gerenciamento de processos com troca de contexto cooperativa (Trabalho 07), paginação de memória virtual no padrão Sv32 (Trabalho 08), suporte a aplicações em espaço de usuário com binário embutido (Trabalho 09) e execução em modo usuário (U-Mode) com isolamento de privilégios e diagnóstico de exceções (Trabalho 10). O funcionamento de todos os módulos foi validado no emulador QEMU.
\end{resumo}

\section{Introdução}

Dando continuidade ao desenvolvimento do kernel bare-metal para a arquitetura RISC-V de 32 bits (RV32), este relatório descreve as atividades realizadas na segunda entrega prática da disciplina de Sistemas Operacionais.

O foco desta etapa foi expandir o kernel básico criado anteriormente, adicionando os mecanismos essenciais de gerenciamento de memória, execução concorrente de tarefas e separação de privilégios entre o kernel e as aplicações de usuário.

Todas as cinco tarefas propostas para esta entrega foram concluídas e testadas no emulador QEMU:
\begin{itemize}
    \item \textbf{Trabalho 06}: Alocação de memória física por páginas de 4~KB;
    \item \textbf{Trabalho 07}: Estrutura de processos, troca de contexto e escalonamento cooperativo;
    \item \textbf{Trabalho 08}: Tabelas de páginas e memória virtual Sv32;
    \item \textbf{Trabalho 09}: Aplicações em espaço de usuário e embutimento de binários;
    \item \textbf{Trabalho 10}: Transição para modo usuário (U-Mode), isolamento de privilégios e tratamento de exceções.
\end{itemize}

\section{Atividades Realizadas}

\subsection{Trabalho 06: Alocação de Memória Física}

Para permitir que o kernel crie estruturas dinamicamente sem recorrer à alocação estática arbitrária, foi implementado um alocador simples de páginas físicas (\textit{bump allocator}).

No linker script (\texttt{kernel.ld}), a região de memória livre foi delimitada logo após a pilha do kernel (\texttt{\_\_stack\_top}). Essa área foi alinhada a 4~KB e configurada com 64~MB de tamanho, demarcada pelos símbolos \texttt{\_\_free\_ram} e \texttt{\_\_free\_ram\_end}:

\begin{verbatim}
    . = ALIGN(4096);
    __free_ram = .;
    . += 64 * 1024 * 1024;
    __free_ram_end = .;
\end{verbatim}

No arquivo \texttt{common.h}, foi definida a constante \texttt{PAGE\_SIZE} como 4096. A função \texttt{alloc\_pages} no arquivo \texttt{kernel.c} gerencia a alocação de $n$ páginas consecutivas. A variável estática \texttt{next\_paddr} mantém o endereço da próxima região livre, iniciando em \texttt{\_\_free\_ram} na primeira chamada. Se a memória solicitada ultrapassar o limite \texttt{\_\_free\_ram\_end}, o kernel interrompe a execução com \texttt{PANIC("out of memory")}. Toda a área alocada é limpa com zeros via \texttt{memset} antes do retorno:

\begin{verbatim}
paddr_t alloc_pages(uint32_t n) {
  static paddr_t next_paddr = 0;
  if (!next_paddr)
    next_paddr = (paddr_t)__free_ram;

  paddr_t paddr = next_paddr;
  next_paddr += n * PAGE_SIZE;

  if (next_paddr > (paddr_t)__free_ram_end)
    PANIC("out of memory");

  memset((void *)paddr, 0, n * PAGE_SIZE);
  return paddr;
}
\end{verbatim}

\subsection{Trabalho 07: Processos e Troca de Contexto}

O sétimo trabalho implementou a estrutura básica para permitir múltiplos processos concorrentes no kernel. No arquivo \texttt{kernel.h}, foi definida a estrutura \texttt{struct process} e a capacidade máxima de 8 processos simultâneos (\texttt{PROCS\_MAX}):

\begin{verbatim}
#define PROCS_MAX 8
#define PROC_UNUSED   0
#define PROC_RUNNABLE 1

struct process {
  int pid;
  int state;
  vaddr_t sp;
  uint32_t *page_table;
  uint8_t stack[8192];
};
\end{verbatim}

Cada processo possui sua própria pilha privativa de 8~KB. Como o escalonamento é cooperativo, a troca de contexto (\texttt{switch\_context}) funciona como uma chamada de função normal segundo a ABI do RISC-V. Dessa forma, é necessário salvar e restaurar apenas os 13 registradores \textit{callee-saved} (\texttt{ra} e \texttt{s0} a \texttt{s11}), enquanto os registradores temporários são preservados pelo compilador:

\begin{verbatim}
__attribute__((naked)) void switch_context(uint32_t *prev_sp,
                                           uint32_t *next_sp) {
  __asm__ __volatile__(
      "addi sp, sp, -13 * 4\n"
      "sw ra,  0  * 4(sp)\n"
      "sw s0,  1  * 4(sp)\n"
      "sw s1,  2  * 4(sp)\n"
      "sw s2,  3  * 4(sp)\n"
      "sw s3,  4  * 4(sp)\n"
      "sw s4,  5  * 4(sp)\n"
      "sw s5,  6  * 4(sp)\n"
      "sw s6,  7  * 4(sp)\n"
      "sw s7,  8  * 4(sp)\n"
      "sw s8,  9  * 4(sp)\n"
      "sw s9,  10 * 4(sp)\n"
      "sw s10, 11 * 4(sp)\n"
      "sw s11, 12 * 4(sp)\n"
      "sw sp, (a0)\n"
      "lw sp, (a1)\n"
      "lw ra,  0  * 4(sp)\n"
      "lw s0,  1  * 4(sp)\n"
      "lw s1,  2  * 4(sp)\n"
      "lw s2,  3  * 4(sp)\n"
      "lw s3,  4  * 4(sp)\n"
      "lw s4,  5  * 4(sp)\n"
      "lw s5,  6  * 4(sp)\n"
      "lw s6,  7  * 4(sp)\n"
      "lw s7,  8  * 4(sp)\n"
      "lw s8,  9  * 4(sp)\n"
      "lw s9,  10 * 4(sp)\n"
      "lw s10, 11 * 4(sp)\n"
      "lw s11, 12 * 4(sp)\n"
      "addi sp, sp, 13 * 4\n"
      "ret\n");
}
\end{verbatim}

A função \texttt{create\_process} busca um slot livre no vetor \texttt{procs}, inicializa a pilha com zeros nos registradores salvos, coloca o endereço de entrada no registrador \texttt{ra} e marca o estado como \texttt{PROC\_RUNNABLE}. A função \texttt{yield} realiza o escalonamento em rodízio (\textit{round-robin}) entre os processos ativos. Antes de chavear o contexto, o topo da pilha do próximo processo é salvo no registrador CSR \texttt{sscratch}, permitindo que o tratador de interrupções preserve a pilha do kernel caso ocorra uma exceção.

\subsection{Trabalho 08: Tabelas de Páginas e Memória Virtual Sv32}

No oitavo trabalho, foi configurado o mecanismo de paginação e isolamento de memória virtual Sv32 do RISC-V. No modelo Sv32, os endereços virtuais de 32 bits são traduzidos em dois níveis: o índice de primeiro nível (\texttt{vpn1}, 10 bits), o índice de segundo nível (\texttt{vpn0}, 10 bits) e o deslocamento da página (12 bits, para páginas de 4~KB).

No arquivo \texttt{kernel.h}, foram definidas as máscaras do registrador \texttt{satp} e os bits de permissão das entradas de tabela de páginas (PTE): \texttt{PAGE\_V} (válida), \texttt{PAGE\_R} (leitura), \texttt{PAGE\_W} (escrita), \texttt{PAGE\_X} (execução) e \texttt{PAGE\_U} (acesso em modo usuário).

A função \texttt{map\_page} em \texttt{kernel.c} gerencia a associação entre endereços virtuais e físicos:

\begin{verbatim}
void map_page(uint32_t *table1, uint32_t vaddr, paddr_t paddr, uint32_t flags) {
  if (!is_aligned(vaddr, PAGE_SIZE))
    PANIC("unaligned vaddr %x", vaddr);
  if (!is_aligned(paddr, PAGE_SIZE))
    PANIC("unaligned paddr %x", paddr);

  uint32_t vpn1 = (vaddr >> 22) & 0x3ff;
  if ((table1[vpn1] & PAGE_V) == 0) {
    uint32_t pt_paddr = alloc_pages(1);
    table1[vpn1] = ((pt_paddr / PAGE_SIZE) << 10) | PAGE_V;
  }

  uint32_t vpn0 = (vaddr >> 12) & 0x3ff;
  uint32_t *table0 = (uint32_t *)((table1[vpn1] >> 10) * PAGE_SIZE);
  table0[vpn0] = ((paddr / PAGE_SIZE) << 10) | flags | PAGE_V;
}
\end{verbatim}

Se a entrada de primeiro nível ainda não existir, uma página é alocada via \texttt{alloc\_pages(1)} para a tabela de segundo nível. Em seguida, a entrada folha correspondente recebe o número da página física (\textit{PPN}) e os bits de controle.

Para manter o código e os dados do kernel acessíveis após ativar a MMU, a função \texttt{create\_process} aloca uma tabela raiz para cada processo e mapeia toda a memória do kernel (\texttt{\_\_kernel\_base} até \texttt{\_\_free\_ram\_end}) em mapeamento identidade ($vaddr = paddr$) com permissões completas (\texttt{rwx}). Durante a troca de processos em \texttt{yield}, o registrador \texttt{satp} é atualizado com o modo Sv32 e o PPN da tabela raiz, utilizando instruções \texttt{sfence.vma} antes e depois para sincronizar a memória e invalidar entradas antigas da TLB.

\subsection{Trabalho 09: Aplicações de Usuário e Embutimento de Binários}

O nono trabalho viabilizou a execução de programas de usuário desacoplados do executável do kernel.

No arquivo \texttt{user.ld}, foi definido o layout de memória das aplicações com endereço base virtual em \texttt{0x1000000} (\texttt{USER\_BASE}), separando o espaço de usuário do espaço do kernel (\texttt{0x80200000}). Foram alocados 64~KB para a pilha do processo (\texttt{\_\_stack\_top}):

\begin{verbatim}
ENTRY(start)
SECTIONS {
    . = 0x1000000;
    .text : { KEEP(*(.text.start)); *(.text .text.*); }
    .rodata : ALIGN(4) { *(.rodata .rodata.*); }
    .data : ALIGN(4) { *(.data .data.*); }
    .bss : ALIGN(4) {
        *(.bss .bss.* .sbss .sbss.*);
        . = ALIGN(16);
        . += 64 * 1024;
        __stack_top = .;
        ASSERT(. < 0x1800000, "too large executable");
    }
}
\end{verbatim}

No arquivo \texttt{user.c}, a rotina inicial em assembly \texttt{start} aponta o registrador \texttt{sp} para \texttt{\_\_stack\_top} e chama a função \texttt{main} do programa. Além disso, implementou-se a função \texttt{putchar} emitindo a instrução \texttt{ecall}, o que permitiu reaproveitar o \texttt{printf} de \texttt{common.c} dentro da aplicação de usuário (\texttt{shell.c}).

Para incluir a aplicação no sistema sem a necessidade de implementar um leitor de ELF no kernel, a ferramenta \texttt{llvm-objcopy} converte o binário compilado (\texttt{shell.elf}) em um arquivo binário plano (\texttt{shell.bin}) e o encapsula como objeto linkável (\texttt{shell.bin.o}):

\begin{verbatim}
llvm-objcopy --set-section-flags .bss=alloc,contents -O binary shell.elf shell.bin
llvm-objcopy -Ibinary -Oelf32-littleriscv shell.bin shell.bin.o
\end{verbatim}

Esses comandos exportam os símbolos \texttt{\_binary\_shell\_bin\_start} e \texttt{\_binary\_shell\_bin\_size}. No kernel, ao carregar a aplicação em \texttt{create\_process}, cada bloco de 4~KB da imagem é copiado com \texttt{memcpy} para páginas físicas dedicadas e mapeado a partir de \texttt{USER\_BASE} com a flag de usuário \texttt{PAGE\_U} ativa.

\subsection{Trabalho 10: Modo Usuário e Isolamento de Privilégios}

O décimo trabalho implementou o isolamento de privilégios da CPU, garantindo que as aplicações executem em Modo Usuário (U-Mode) e que qualquer instrução restrita ou acesso à memória física do kernel seja interceptado diretamente pelo hardware.

A transição para U-Mode é realizada pela rotina trampolim \texttt{user\_entry}:

\begin{verbatim}
__attribute__((naked)) void user_entry(void) {
  __asm__ __volatile__(
      "csrw sepc, %[sepc]\n"
      "csrw sstatus, %[sstatus]\n"
      "sret\n"
      :
      : [sepc] "r"(USER_BASE),
        [sstatus] "r"(SSTATUS_SPIE));
}
\end{verbatim}

A instrução \texttt{sret} executa três passos controlados pelo hardware:
\begin{enumerate}
    \item Salta o contador de programa ($pc$) para o endereço gravado em \texttt{sepc} (\texttt{USER\_BASE});
    \item Altera o nível de privilégio da CPU para o valor presente no campo \texttt{SPP} de \texttt{sstatus}. Como gravamos apenas \texttt{SSTATUS\_SPIE}, o campo \texttt{SPP} permanece em 0, comutando a CPU para U-Mode;
    \item Restaura a habilitação das interrupções de supervisor copiando o bit \texttt{SPIE} para \texttt{SIE}.
\end{enumerate}

O isolamento de memória é garantido pelas permissões da tabela Sv32: apenas as páginas da aplicação possuem a flag \texttt{PAGE\_U}. As páginas do kernel possuem apenas permissões de supervisor, gerando imediatamente uma falta de página (\textit{Page Fault}) caso U-Mode tente acessá-las. Da mesma forma, instruções restritas (como \texttt{csrr}, \texttt{csrw} ou \texttt{sret}) disparam uma exceção de instrução ilegal se executadas em U-Mode.

Por fim, a função \texttt{handle\_trap} em \texttt{kernel.c} foi estruturada para identificar a causa da exceção (\texttt{scause}). Quando \texttt{scause == 8} (chamada de sistema via \texttt{ecall} em U-Mode), o kernel imprime o caractere em \texttt{a0}, avança \texttt{sepc} em 4 bytes e retorna normalmente. Para qualquer outra exceção inesperada, o kernel imprime a causa, o endereço de falha (\texttt{sepc}) e o valor de contexto (\texttt{stval}), interrompendo a CPU de forma segura através de \texttt{PANIC}:

\begin{verbatim}
void handle_trap(struct trap_frame *f) {
  uint32_t scause = READ_CSR(scause);
  uint32_t stval = READ_CSR(stval);
  uint32_t user_pc = READ_CSR(sepc);

  if (scause == 8) {
    putchar(f->a0);
    user_pc += 4;
    WRITE_CSR(sepc, user_pc);
    return;
  }

  const char *desc = "unknown trap";
  switch (scause) {
    case 0:  desc = "instruction address misaligned"; break;
    case 1:  desc = "instruction access fault"; break;
    case 2:  desc = "illegal instruction"; break;
    case 3:  desc = "breakpoint"; break;
    case 4:  desc = "load address misaligned"; break;
    case 5:  desc = "load access fault"; break;
    case 6:  desc = "store/amo address misaligned"; break;
    case 7:  desc = "store/amo access fault"; break;
    case 12: desc = "instruction page fault"; break;
    case 13: desc = "load page fault"; break;
    case 15: desc = "store/amo page fault"; break;
  }

  printf("Trap: %s (scause=%x, stval=%x, sepc=%x)\n",
         desc, scause, stval, user_pc);
  PANIC("unexpected trap scause=%x, stval=%x, sepc=%x",
        scause, stval, user_pc);
}
\end{verbatim}

\section{Atividades Não Realizadas}

Diferente da primeira entrega, todas as cinco etapas previstas para a Entrega 2 (Trabalhos 06 a 10) foram concluídas e testadas com sucesso.

Ficaram para a etapa seguinte (Entrega 3) os recursos mais avançados do sistema operacional, como o sistema de arquivos virtual (TarFS), uma biblioteca de chamadas de sistema mais completa no padrão POSIX e o escalonamento preemptivo com interrupções de temporizador.

\section{Resultados e Validação}

O código foi compilado com o Clang/LLD para RISC-V 32-bit em modo \textit{freestanding} e testado no QEMU via script \texttt{run.sh}.

Os testes confirmaram o funcionamento das etapas desenvolvidas:
\begin{enumerate}
    \item \textbf{Alocação de Memória Física:} Na inicialização, a chamada de teste de \texttt{alloc\_pages} no \texttt{kernel\_main} confirmou o avanço sequencial dos blocos:
\begin{verbatim}
alloc_pages test: paddr0=80231000
alloc_pages test: paddr1=80233000
\end{verbatim}
    O endereço \texttt{paddr0} inicia em \texttt{\_\_free\_ram} (alinhado a 4~KB) e \texttt{paddr1} avança exatamente duas páginas (8192 bytes), confirmando que a alocação é contínua e sem sobreposição.

    \item \textbf{Troca de Contexto e Escalonamento:} Foram criados dois processos cooperativos no kernel emitindo caracteres alternados e cedendo a CPU voluntariamente via \texttt{yield}:
\begin{verbatim}
starting process A
Astarting process B
BABABABABABABABABABABABABABABABABABABABABABABABABABABABA...
\end{verbatim}
    A saída comprovou que a troca de contexto preserva os registradores e a pilha privativa de cada tarefa.

    \item \textbf{Paginação Sv32 e MMU:} Pelo monitor do QEMU (\texttt{Ctrl+A C}), o comando \texttt{info registers} confirmou \texttt{satp = 80080246}, comprovando que o modo Sv32 está ativo com a tabela raiz do processo atual. O comando \texttt{info mem} confirmou o mapeamento identidade do kernel de \texttt{0x80200000} até \texttt{0x84231000} com permissões \texttt{rwx}.

    \item \textbf{Aplicação de Usuário e Binário Embutido:} O binário \texttt{shell.bin} (66.256 bytes) foi embutido no kernel via \texttt{shell.bin.o}. No boot, o processo foi carregado em \texttt{USER\_BASE} (\texttt{0x1000000}) e executou em U-Mode:
\begin{verbatim}
shell_bin size = 66256
shell_bin[0] = 37
Hello World from user application (shell)!
[shell] application is running...
[shell] application is running...
\end{verbatim}
    A recepção contínua das mensagens confirmou a execução do código de usuário e o tratamento das chamadas \texttt{ecall} pelo kernel (\texttt{scause = 8}).

    \item \textbf{Isolamento de Privilégios e Exceções:} A proteção de hardware foi validada através de dois testes intencionais:
    \begin{itemize}
        \item \textit{Instrução Privilegiada:} A execução de \texttt{csrr t0, sstatus} a partir do código de usuário foi barrada pelo hardware, disparando a exceção de instrução ilegal:
\begin{verbatim}
Trap: illegal instruction (scause=00000002, stval=100022f3, sepc=0100001c)
PANIC: kernel.c:92: unexpected trap scause=00000002, stval=100022f3, sepc=0100001c
\end{verbatim}
        \item \textit{Acesso à Memória do Kernel:} A tentativa de escrita no endereço \texttt{0x80200000} a partir de U-Mode violou as permissões da MMU, gerando falta de página:
\begin{verbatim}
Trap: store/amo page fault (scause=0000000f, stval=80200000, sepc=01000026)
PANIC: kernel.c:92: unexpected trap scause=0000000f, stval=80200000, sepc=01000026
\end{verbatim}
    \end{itemize}
    Ambos os cenários comprovaram que acessos indevidos interrompem o sistema de forma controlada através de \texttt{PANIC}, exibindo as causas e registradores com clareza.
\end{enumerate}

\section{Conclusão}

Nesta segunda etapa, o kernel evoluiu com a implementação de alocação de memória física por páginas, gerenciamento de múltiplos processos com troca de contexto cooperativa, memória virtual com paginação Sv32 e a execução de aplicações independentes em Modo Usuário com isolamento por hardware e tratamento de exceções. Todas as etapas previstas foram concluídas e testadas no QEMU, deixando o sistema preparado para receber o sistema de arquivos e as chamadas de sistema na Entrega 3.
