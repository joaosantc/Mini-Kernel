\begin{abstract}
This report documents the continuation of the minimal 32-bit RISC-V operating system kernel, completing the full scope of the second project milestone. The accomplished tasks encompass physical memory management via a page-aligned bump allocator (Task 6), process infrastructure featuring dedicated process control blocks, private stacks, assembly context switching, cooperative round-robin scheduling, and kernel stack isolation using the sscratch register (Task 7), two-level Sv32 virtual memory management with identity mapping and MMU activation via the satp register (Task 8), userland application memory layout, minimal runtime library, object-based binary embedding, and application dispatch (Task 9), as well as CPU privilege transition to user mode (U-Mode) via sret, CSR configuration, user page permissions, hardware-enforced privilege isolation, and controlled trap exception diagnostics (Task 10). The entire system was validated on the QEMU emulator.
\end{abstract}

\begin{resumo}
Este relatório descreve a evolução de um kernel mínimo para a arquitetura RISC-V de 32 bits, concluindo integralmente o escopo da segunda entrega prática. Foram implementados o alocador dinâmico de páginas de memória física alinhadas a 4~KB (Trabalho 06), a infraestrutura de processos com blocos de controle (PCB), pilhas privativas, troca de contexto em assembly, escalonamento cooperativo e proteção da pilha de interrupção com o registrador sscratch (Trabalho 07), o gerenciamento de memória virtual Sv32 em dois níveis com chaveamento de MMU via satp (Trabalho 08), o suporte à construção e embutimento de aplicações no espaço de usuário com runtime mínimo (Trabalho 09), e a transição de privilégio da CPU para o modo usuário (U-Mode) via instrução sret, configuração dos registradores CSR, isolamento de privilégio de instruções e memória por hardware, e diagnóstico controlado de exceções (Trabalho 10). Todas as implementações foram validadas no emulador QEMU.
\end{resumo}

\section{Atividades Realizadas}

\subsection{Trabalho 06: Alocação de Memória Física}

Para permitir a criação dinâmica de estruturas pelo kernel sem recorrer à alocação estática arbitrária, foi implementado um alocador de páginas físicas baseado na estratégia \textit{Bump Allocator} (ou alocador linear).

A delimitação da memória disponível foi realizada diretamente no linker script (\texttt{kernel.ld}), logo após o espaço reservado para a pilha do kernel (\texttt{\_\_stack\_top}). A área foi alinhada a uma fronteira de 4096 bytes (4~KB) e estendida em 64~MB, demarcada pelos símbolos \texttt{\_\_free\_ram} e \texttt{\_\_free\_ram\_end}:

\begin{verbatim}
    . = ALIGN(4096);
    __free_ram = .;
    . += 64 * 1024 * 1024;
    __free_ram_end = .;
\end{verbatim}

No arquivo \texttt{common.h}, foi definida a constante fundamental \texttt{PAGE\_SIZE} como 4096. A função \texttt{alloc\_pages} no arquivo \texttt{kernel.c} gerencia a alocação de $n$ páginas consecutivas. A variável estática \texttt{next\_paddr} mantém o endereço da próxima região livre. A inicialização é resolvida dinamicamente no primeiro ciclo para garantir estrita conformidade com expressões constantes em C:

\begin{verbatim}
paddr_t alloc_pages(uint32_t n) {
  static paddr_t next_paddr = 0;
  if (!next_paddr)
    next_paddr = (paddr_t)__free_ram;

  paddr_t paddr = next_paddr;
  next_paddr += n * PAGE_SIZE;

  if (next_paddr > (paddr_t)__free_ram_end)
    PANIC("out of memory");

  memset((void *)paddr, 0, n * PAGE_SIZE);
  return paddr;
}
\end{verbatim}

A função assegura três invariantes:
\begin{enumerate}
    \item Os endereços retornados são múltiplos exatos de 4~KB;
    \item Em caso de esgotamento do limite superior (\texttt{\_\_free\_ram\_end}), dispara-se \texttt{PANIC("out of memory")};
    \item A memória retornada é integralmente limpa com zeros via \texttt{memset}, evitando a propagação de lixo de memória.
\end{enumerate}

\subsection{Trabalho 07: Processos e Troca de Contexto}

O sétimo trabalho viabilizou a execução concorrente de tarefas no kernel. No arquivo \texttt{kernel.h}, foi definido o Bloco de Controle de Processo (\texttt{struct process}) e a capacidade máxima de processos no sistema (\texttt{PROCS\_MAX = 8}):

\begin{verbatim}
#define PROCS_MAX 8
#define PROC_UNUSED   0
#define PROC_RUNNABLE 1

struct process {
  int pid;
  int state;
  vaddr_t sp;
  uint32_t *page_table;
  uint8_t stack[8192];
};
\end{verbatim}

Cada processo possui sua própria pilha de execução com 8~KB de extensão, eliminando a dependência de pilha única global.

A rotina de troca de contexto (\texttt{switch\_context}) foi implementada em assembly com o atributo \texttt{naked}. Seguindo a convenção de chamada da ABI RISC-V, apenas os 13 registradores \textit{callee-saved} (\texttt{ra} e \texttt{s0} a \texttt{s11}) necessitam de salvamento na pilha da tarefa corrente, uma vez que os registradores temporários (\textit{caller-saved}) já são geridos pelo compilador no momento da invocação:

\begin{verbatim}
__attribute__((naked)) void switch_context(uint32_t *prev_sp,
                                           uint32_t *next_sp) {
  __asm__ __volatile__(
      "addi sp, sp, -13 * 4\n"
      "sw ra,  0  * 4(sp)\n"
      "sw s0,  1  * 4(sp)\n"
      "sw s1,  2  * 4(sp)\n"
      "sw s2,  3  * 4(sp)\n"
      "sw s3,  4  * 4(sp)\n"
      "sw s4,  5  * 4(sp)\n"
      "sw s5,  6  * 4(sp)\n"
      "sw s6,  7  * 4(sp)\n"
      "sw s7,  8  * 4(sp)\n"
      "sw s8,  9  * 4(sp)\n"
      "sw s9,  10 * 4(sp)\n"
      "sw s10, 11 * 4(sp)\n"
      "sw s11, 12 * 4(sp)\n"
      "sw sp, (a0)\n"
      "lw sp, (a1)\n"
      "lw ra,  0  * 4(sp)\n"
      "lw s0,  1  * 4(sp)\n"
      "lw s1,  2  * 4(sp)\n"
      "lw s2,  3  * 4(sp)\n"
      "lw s3,  4  * 4(sp)\n"
      "lw s4,  5  * 4(sp)\n"
      "lw s5,  6  * 4(sp)\n"
      "lw s6,  7  * 4(sp)\n"
      "lw s7,  8  * 4(sp)\n"
      "lw s8,  9  * 4(sp)\n"
      "lw s9,  10 * 4(sp)\n"
      "lw s10, 11 * 4(sp)\n"
      "lw s11, 12 * 4(sp)\n"
      "addi sp, sp, 13 * 4\n"
      "ret\n");
}
\end{verbatim}

A função \texttt{create\_process} aloca um descritor livre na tabela estática \texttt{procs}, monta a estrutura inicial da pilha empilhando zeros para os registradores salvos e o endereço de entrada no registrador \texttt{ra}, ajustando o estado para \texttt{PROC\_RUNNABLE}.

O escalonador cooperativo (\texttt{yield}) realiza a busca circular em rodízio pelo próximo processo executável com \texttt{pid > 0}. Caso nenhum outro processo esteja pronto, o \texttt{idle\_proc} (PID 0) é selecionado. Durante a transição, a base da pilha do próximo processo é gravada no registrador CSR \texttt{sscratch}, permitindo que o tratador \texttt{kernel\_entry} recupere de forma segura a pilha privativa do processo através da instrução \texttt{csrrw sp, sscratch, sp}.

\subsection{Trabalho 08: Tabelas de Páginas e Memória Virtual Sv32}

O oitavo trabalho introduziu o suporte ao mecanismo de tradução e isolamento de memória virtual Sv32 do RISC-V. No modelo Sv32, os endereços virtuais de 32 bits são decompostos em dois níveis hierárquicos: o índice de primeiro nível ($VPN[1]$, 10 bits), o índice de segundo nível ($VPN[0]$, 10 bits) e o deslocamento dentro da página ($Offset$, 12 bits).

No arquivo \texttt{kernel.h}, foram estabelecidas as definições de controle do registrador \texttt{satp} e das entradas da tabela de páginas (PTE):
\begin{verbatim}
#define SATP_SV32 (1u << 31)
#define PAGE_V    (1 << 0) // Entrada válida
#define PAGE_R    (1 << 1) // Permissão de leitura
#define PAGE_W    (1 << 2) // Permissão de escrita
#define PAGE_X    (1 << 3) // Permissão de execução
#define PAGE_U    (1 << 4) // Acesso em modo usuário
\end{verbatim}

A estrutura de processo (\texttt{struct process}) foi atualizada para conter o ponteiro da tabela raiz de primeiro nível (\texttt{uint32\_t *page\_table}).

No linker script (\texttt{kernel.ld}), exportou-se o símbolo \texttt{\_\_kernel\_base = .;} logo após a atribuição do endereço base em \texttt{0x80200000}, estabelecendo a fronteira inferior da memória física ocupada pela imagem do kernel.

A função \texttt{map\_page} em \texttt{kernel.c} gerencia a associação entre endereços virtuais e físicos em blocos alinhados a 4~KB:
\begin{verbatim}
void map_page(uint32_t *table1, uint32_t vaddr, paddr_t paddr, uint32_t flags) {
  if (!is_aligned(vaddr, PAGE_SIZE))
    PANIC("unaligned vaddr %x", vaddr);

  if (!is_aligned(paddr, PAGE_SIZE))
    PANIC("unaligned paddr %x", paddr);

  uint32_t vpn1 = (vaddr >> 22) & 0x3ff;
  if ((table1[vpn1] & PAGE_V) == 0) {
    uint32_t pt_paddr = alloc_pages(1);
    table1[vpn1] = ((pt_paddr / PAGE_SIZE) << 10) | PAGE_V;
  }

  uint32_t vpn0 = (vaddr >> 12) & 0x3ff;
  uint32_t *table0 = (uint32_t *)((table1[vpn1] >> 10) * PAGE_SIZE);
  table0[vpn0] = ((paddr / PAGE_SIZE) << 10) | flags | PAGE_V;
}
\end{verbatim}

Quando uma entrada de primeiro nível ainda não existe (\texttt{PAGE\_V == 0}), a função aloca dinamicamente uma página para a tabela de segundo nível através de \texttt{alloc\_pages(1)}. Em seguida, a entrada folha correspondente é gravada com o número da página física ($PPN = paddr / PAGE\_SIZE$), as flags de permissão e o bit de validade.

Na função \texttt{create\_process}, cada tarefa recebe uma tabela de páginas raiz. Para garantir que o código e as estruturas do kernel permaneçam acessíveis após a ativação da MMU, realiza-se o mapeamento identidade ($vaddr = paddr$) em toda a faixa de \texttt{\_\_kernel\_base} até \texttt{\_\_free\_ram\_end} com permissões completas (\texttt{PAGE\_R | PAGE\_W | PAGE\_X}):
\begin{verbatim}
  uint32_t *page_table = (uint32_t *)alloc_pages(1);
  for (paddr_t paddr = (paddr_t)__kernel_base;
       paddr < (paddr_t)__free_ram_end; paddr += PAGE_SIZE)
    map_page(page_table, paddr, paddr, PAGE_R | PAGE_W | PAGE_X);

  proc->page_table = page_table;
\end{verbatim}

Durante a troca de processos em \texttt{yield}, a MMU é atualizada gravando-se no registrador \texttt{satp} o identificador de modo \texttt{SATP\_SV32} combinado com o PPN da tabela raiz do próximo processo. A escrita no \texttt{satp} é envolvida por instruções \texttt{sfence.vma} antes e depois, garantindo a conclusão das alterações em memória e a invalidação de entradas obsoletas na TLB:
\begin{verbatim}
  __asm__ __volatile__(
      "sfence.vma\n"
      "csrw satp, %[satp]\n"
      "sfence.vma\n"
      "csrw sscratch, %[sscratch]\n"
      :
      : [satp] "r"(SATP_SV32 | ((uint32_t)next->page_table / PAGE_SIZE)),
        [sscratch] "r"((uint32_t)&next->stack[sizeof(next->stack)]));
\end{verbatim}

\subsection{Trabalho 09: Aplicações de Usuário e Embutimento de Binários}

O nono trabalho estabeleceu o suporte à execução de código de usuário dissociado da imagem do kernel. O modelo adotado segrega fisicamente o espaço de endereçamento, provê uma biblioteca de runtime mínima para a aplicação e embute o binário resultante no executável do kernel através de encapsulamento ELF.

\subsubsection{Layout de Memória e Linker Script da Aplicação}

No arquivo \texttt{user.ld}, foi definido o layout de memória específico da aplicação em espaço de usuário, com endereço virtual base em \texttt{0x1000000} (\texttt{USER\_BASE}), garantindo o desacoplamento do espaço do kernel (\texttt{0x80200000}):

\begin{verbatim}
ENTRY(start)

SECTIONS {
    . = 0x1000000;

    .text :{
        KEEP(*(.text.start));
        *(.text .text.*);
    }

    .rodata : ALIGN(4) {
        *(.rodata .rodata.*);
    }

    .data : ALIGN(4) {
        *(.data .data.*);
    }

    .bss : ALIGN(4) {
        *(.bss .bss.* .sbss .sbss.*);

        . = ALIGN(16);
        . += 64 * 1024; /* 64KB */
        __stack_top = .;

        ASSERT(. < 0x1800000, "too large executable");
    }
}
\end{verbatim}

A seção \texttt{.text.start} fixa a rotina \texttt{start} no início do executável. O linker script aloca 64~KB para a pilha do processo (\texttt{\_\_stack\_top}) e aplica uma asserção estática impedindo que a imagem ultrapasse o limite de \texttt{0x1800000}.

\subsubsection{Runtime Mínimo de Usuário e Aplicação Shell}

No arquivo \texttt{user.c}, foi implementada a rotina de inicialização em assembly puro (\texttt{start}), responsável por preparar o registrador \texttt{sp} de usuário e transferir o controle para a função \texttt{main} da aplicação:

\begin{verbatim}
__attribute__((section(".text.start"))) __attribute__((naked)) void start(void) {
  __asm__ __volatile__("mv sp, %[stack_top] \n"
                       "call main           \n"
                       "call exit           \n"
                       ::[stack_top] "r"(__stack_top));
}
\end{verbatim}

A função \texttt{exit} entra em laço infinito, e a primitiva \texttt{putchar} foi implementada para emitir uma instrução \texttt{ecall}, viabilizando o uso de \texttt{printf} (proveniente de \texttt{common.c}) no espaço de usuário. A aplicação (\texttt{shell.c}) emite uma mensagem inicial identificável e itera emitindo notificações periódicas de execução.

\subsubsection{Conversão e Embutimento do Binário}

Para evitar complexidade excessiva com parsers de formato ELF no kernel, a aplicação é compilada como um arquivo ELF (\texttt{shell.elf}) e convertida em um binário plano (\textit{raw binary}, \texttt{shell.bin}) via \texttt{llvm-objcopy}:

\begin{verbatim}
llvm-objcopy --set-section-flags .bss=alloc,contents -O binary shell.elf shell.bin
llvm-objcopy -Ibinary -Oelf32-littleriscv shell.bin shell.bin.o
\end{verbatim}

O segundo comando empacota a imagem binária crua em um arquivo objeto ELF linkável (\texttt{shell.bin.o}), exportando os símbolos absolutos \texttt{\_binary\_shell\_bin\_start} e \texttt{\_binary\_shell\_bin\_size}.

\subsubsection{Carregamento e Mapeamento de Páginas no Kernel}

No kernel, a função \texttt{create\_process} foi atualizada para aceitar o ponteiro da imagem e seu tamanho. Cada bloco de 4~KB da imagem é copiado via \texttt{memcpy} para uma página física isolada alocada dinamicamente, sendo mapeado na tabela Sv32 em \texttt{USER\_BASE + offset} com as permissões de usuário \texttt{PAGE\_U | PAGE\_R | PAGE\_W | PAGE\_X}:

\begin{verbatim}
  if (image) {
    for (uint32_t off = 0; off < image_size; off += PAGE_SIZE) {
      paddr_t page = alloc_pages(1);
      size_t remaining = image_size - off;
      size_t copy_size = PAGE_SIZE <= remaining ? PAGE_SIZE : remaining;
      memcpy((void *)page, (const char *)image + off, copy_size);
      map_page(page_table, USER_BASE + off, page,
               PAGE_U | PAGE_R | PAGE_W | PAGE_X);
    }
  }
\end{verbatim}

A cópia física dedicada assegura que múltiplos processos não compartilhem páginas mutáveis. O registrador inicial \texttt{ra} da pilha do processo é inicializado com o endereço de \texttt{user\_entry}, um trampolim que grava \texttt{sepc = USER\_BASE}, ativa \texttt{SSTATUS\_SPIE} e executa \texttt{sret}. O tratador de traps (\texttt{handle\_trap}) intercepta chamadas \texttt{scause == 8}, imprimindo o caractere passado em \texttt{a0} e incrementando \texttt{sepc} em 4 bytes para retorno transparente.

Para garantir compatibilidade com compilações agregadas em sistemas avaliadores sem causar colisões de símbolos no vinculador, as definições de \texttt{putchar} e as declarações externas de \texttt{\_binary\_shell\_bin\_start} e \texttt{\_binary\_shell\_bin\_size} foram anotadas com o atributo fraco (\texttt{\_\_attribute\_\_((weak))}).

\subsection{Trabalho 10: Modo Usuário e Isolamento de Privilégios}

O décimo trabalho implementou a barreira formal de privilégio entre o sistema operacional (S-Mode) e as aplicações (U-Mode), garantindo que instruções restritas e acessos indevidos à memória física do kernel sejam interceptados diretamente pelo hardware da CPU.

\subsubsection{Transição de Nível de Privilégio via \texttt{sret}}

A transição controlada para U-Mode é realizada pela rotina trampolim \texttt{user\_entry}, implementada com o atributo \texttt{naked}:

\begin{verbatim}
__attribute__((naked)) void user_entry(void) {
  __asm__ __volatile__(
      "csrw sepc, %[sepc]\n"
      "csrw sstatus, %[sstatus]\n"
      "sret\n"
      :
      : [sepc] "r"(USER_BASE),
        [sstatus] "r"(SSTATUS_SPIE));
}
\end{verbatim}

A instrução \texttt{sret} (\textit{Supervisor Return}) executa três ações coordenadas pelo hardware RISC-V:
\begin{enumerate}
    \item O contador de programa ($pc$) é atualizado com o valor armazenado no registrador CSR \texttt{sepc} (definido como \texttt{USER\_BASE = 0x1000000});
    \item O nível de privilégio da CPU é alterado para o valor presente no campo \texttt{SPP} (\textit{Supervisor Previous Privilege}, bit 8) do registrador \texttt{sstatus}. Como o valor gravado possui apenas o bit \texttt{SSTATUS\_SPIE} (bit 5) ativo, o campo \texttt{SPP} permanece em 0, forçando a CPU para o nível U-Mode;
    \item As interrupções em nível de supervisor são reabilitadas transferindo o bit \texttt{SPIE} para \texttt{SIE}, e \texttt{SPIE} é redefinido para 1.
\end{enumerate}

\subsubsection{Configuração da Pilha e Proteção de Trap}

Ao ingressar em \texttt{start}, a aplicação define o registrador de pilha de usuário \texttt{sp} para o topo da região reservada (\texttt{\_\_stack\_top}), situada no espaço virtual mapeado com permissão de usuário. Durante uma armadilha (\textit{trap}), a instrução \texttt{csrrw sp, sscratch, sp} em \texttt{kernel\_entry} comuta a pilha de usuário não-confiável pela pilha privativa do processo no kernel, mantendo o isolamento de execução entre os níveis.

\subsubsection{Garantia de Isolamento de Memória}

Na tabela Sv32 do processo, apenas as páginas copiadas da aplicação em \texttt{USER\_BASE} recebem o bit \texttt{PAGE\_U}. As páginas de código e dados do kernel (\texttt{\_\_kernel\_base} a \texttt{\_\_free\_ram\_end}) possuem apenas as permissões \texttt{PAGE\_R | PAGE\_W | PAGE\_X}. Consequentemente, qualquer tentativa de leitura, escrita ou salto a partir de U-Mode para a faixa do kernel viola as regras de tradução da MMU, gerando imediatamente uma falha de página (\textit{Page Fault}).

\subsubsection{Diagnóstico e Tratamento Controlado de Exceções}

Para atender ao requisito de diagnóstico claro de exceções, a rotina \texttt{handle\_trap} em \texttt{kernel.c} decodifica a causa da interrupção (\texttt{scause}):

\begin{verbatim}
void handle_trap(struct trap_frame *f) {
  uint32_t scause = READ_CSR(scause);
  uint32_t stval = READ_CSR(stval);
  uint32_t user_pc = READ_CSR(sepc);

  if (scause == 8) {
    putchar(f->a0);
    user_pc += 4;
    WRITE_CSR(sepc, user_pc);
    return;
  }

  const char *desc = "unknown trap";
  switch (scause) {
    case 0:  desc = "instruction address misaligned"; break;
    case 1:  desc = "instruction access fault"; break;
    case 2:  desc = "illegal instruction"; break;
    case 3:  desc = "breakpoint"; break;
    case 4:  desc = "load address misaligned"; break;
    case 5:  desc = "load access fault"; break;
    case 6:  desc = "store/amo address misaligned"; break;
    case 7:  desc = "store/amo access fault"; break;
    case 12: desc = "instruction page fault"; break;
    case 13: desc = "load page fault"; break;
    case 15: desc = "store/amo page fault"; break;
  }

  printf("Trap: %s (scause=%x, stval=%x, sepc=%x)\n", desc, scause, stval,
         user_pc);
  PANIC("unexpected trap scause=%x, stval=%x, sepc=%x", scause, stval,
        user_pc);
}
\end{verbatim}

Quando uma aplicação em U-Mode tenta executar instruções restritas de controle e status (como \texttt{csrr} ou \texttt{csrw} direcionadas a registradores de supervisor, \texttt{sret} ou \texttt{wfi}), a CPU dispara a exceção de instrução ilegal (\texttt{scause = 2}). Se houver tentativa de escrita ou leitura na memória reservada do kernel, a MMU sinaliza falha de página (\texttt{scause = 13} ou \texttt{15}). Em ambos os casos, o kernel captura o evento, imprime a descrição formal do erro, o endereço da falha (\texttt{sepc}) e o valor de contexto (\texttt{stval}), contendo o sistema em estado seguro sem reboots descontrolados.

\section{Resultados e Validação}

O código foi compilado através do Clang/LLD com as opções \texttt{-ffreestanding -nostdlib -O2} e verificado no QEMU (\texttt{run.sh}).

\begin{enumerate}
    \item \textbf{Validação da Alocação de Páginas:} A inspeção dos símbolos via \texttt{llvm-nm} confirmou que \texttt{\_\_free\_ram} foi alocado em \texttt{0x80231000} e \texttt{\_\_free\_ram\_end} em \texttt{0x84231000}, respeitando o alinhamento de 4~KB e a extensão de 64~MB. A chamada de teste em \texttt{kernel\_main} gerou a saída serial esperada:
\begin{verbatim}
alloc_pages test: paddr0=80231000
alloc_pages test: paddr1=80233000
\end{verbatim}
    O endereço \texttt{paddr0} coincide com a base da memória livre, e \texttt{paddr1} situa-se exatamente 8192 bytes (2 páginas) à frente, confirmando a ausência de sobreposição.

    \item \textbf{Validação da Troca de Contexto e Escalonamento:} Foram criados dois processos concorrentes (\texttt{proc\_a} e \texttt{proc\_b}) que emitem repetidamente os caracteres \texttt{'A'} e \texttt{'B'}, cedendo a CPU voluntariamente via \texttt{yield}:
\begin{verbatim}
starting process A
Astarting process B
BABABABABABABABABABABABABABABABABABABABABABABABABABABABA...
\end{verbatim}
    A saída confirma que a alternância de fluxo ocorre de forma contínua e determinística, preservando o estado interno dos registradores e os ponteiros de pilha individuais de cada tarefa.

    \item \textbf{Validação da Paginação Sv32 e MMU:} A ativação da MMU e a integridade das tabelas foram comprovadas diretamente pelo monitor do QEMU:
    \begin{itemize}
        \item O comando \texttt{info registers} confirmou o registrador \texttt{satp = 80080246}, demonstrando que o bit 31 (\texttt{SATP\_SV32}) está ativo e que o PPN raiz aponta para o endereço físico correspondente da tabela de primeiro nível alocada.
        \item O comando \texttt{info mem} confirmou o mapeamento identidade integral do kernel de \texttt{0x80200000} até \texttt{0x84231000} com atributos de permissão \texttt{rwx}.
        \item A execução contínua dos processos sob paginação ativa ocorreu sem geração de falhas espúrias. Ademais, eventuais acessos inválidos a regiões não mapeadas são interceptados pelo tratador de interrupções (\texttt{handle\_trap}) via \texttt{stvec}, emitindo um pânico controlado sem reiniciar o processador.
    \end{itemize}

    \item \textbf{Validação das Aplicações de Usuário e Embutimento de Binário:} A cadeia de construção automatizada gerou o binário plano \texttt{shell.bin} (66.256 bytes) e o vinculou ao kernel através de \texttt{shell.bin.o}. No QEMU, a inspeção via monitor confirmou o mapeamento correto da faixa \texttt{0x01000000} com atributos de usuário (\texttt{rwxu}) sobre a memória física alocada.
    
    A execução serial comprovou o chaveamento de contexto, a transição para a rotina de usuário e a saída contínua do shell:
\begin{verbatim}
shell_bin size = 66256
shell_bin[0] = 37
Hello World from user application (shell)!
[shell] application is running...
[shell] application is running...
\end{verbatim}
    A recepção regular das mensagens comprovou que a chamada \texttt{ecall} oriunda da aplicação de usuário foi interceptada com sucesso pelo tratador do kernel (\texttt{scause = 8}), confirmando a integração ponta a ponta do runtime e do tratador de interrupções.

    \item \textbf{Validação do Modo Usuário e Isolamento de Privilégios:} A eficácia da separação de privilégios foi comprovada através de testes dedicados em ambiente emulado:
    \begin{itemize}
        \item \textit{Transição e Execução em U-Mode:} O boot do kernel e o chaveamento com \texttt{sret} posicionaram a execução no endereço \texttt{0x01000000}, com a aplicação shell emitindo mensagens contínuas no terminal serial via \texttt{ecall}.
        \item \textit{Contenção de Instrução Privilegiada:} Ao injetar a instrução \texttt{csrr t0, sstatus} na aplicação de usuário, o hardware rejeitou a operação e gerou a exceção de instrução ilegal:
\begin{verbatim}
Trap: illegal instruction (scause=00000002, stval=100022f3, sepc=0100001c)
PANIC: kernel.c:93: unexpected trap scause=00000002, stval=100022f3, sepc=0100001c
\end{verbatim}
        O valor de \texttt{stval} capturou o opcode da instrução inválida e o \texttt{sepc} apontou com precisão para a instrução na aplicação.
        \item \textit{Contenção de Acesso à Memória do Kernel:} Ao forçar uma gravação no endereço de kernel \texttt{0x80200000} a partir do código de usuário, a MMU bloqueou o acesso devido à ausência do bit \texttt{PAGE\_U}, disparando a falha de página controlada:
\begin{verbatim}
Trap: store/amo page fault (scause=0000000f, stval=80200000, sepc=01000026)
PANIC: kernel.c:93: unexpected trap scause=0000000f, stval=80200000, sepc=01000026
\end{verbatim}
    \end{itemize}
    Ambos os cenários comprovaram a robustez do isolamento de hardware e a clareza do diagnóstico emitido pelo kernel.
\end{enumerate}

\section{Conclusão}

As atividades desenvolvidas nesta segunda etapa dotaram o kernel de recursos fundamentais de infraestrutura de sistemas operacionais: alocação dinâmica de memória física por páginas alinhadas, concorrência cooperativa de processos com pilhas dedicadas, gerenciamento de memória virtual paginada sob a arquitetura Sv32 do RISC-V, embutimento e execução de binários independentes no espaço de usuário com runtime próprio, e isolamento formal de privilégios de CPU em modo usuário (U-Mode) com diagnóstico controlado de exceções. O kernel encontra-se preparado para o desenvolvimento da terceira etapa, com foco em chamadas de sistema estruturadas e sistema de arquivos.
